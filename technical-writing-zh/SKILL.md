# 中文技术写作

把技术事实写成目标读者一次能看懂、能够用于判断或行动的文本。先修正文档结构和事实表达，再处理句子风格。不要为了显得自然而删除条件、制造口语感或改变技术含义。

## 先确认任务

开始前确定：

1. 谁会读这份文档。
2. 读者要据此判断、实现还是操作什么。
3. 用户要审阅问题、直接改写，还是修改文件。
4. 文本属于技术说明、操作步骤，还是包含个人观点的复盘。

信息足够时直接处理，不为确认显而易见的受众或格式而提问。

## 选择检查范围

处理技术方案、设计文档、README 或操作说明时，必须读取：

- [references/controlled-language.md](references/controlled-language.md)，检查术语来源、缩写、动词、模态词和一词一义；
- [references/technical-writing.md](references/technical-writing.md)，检查读者任务、完整过程、抽象层级和事实保护。

处理技术方案、接口契约、架构评审，或文档包含图表和代码示例时，还必须读取 [references/contract-and-artifact-review.md](references/contract-and-artifact-review.md)，检查跨章节契约、单位与身份字段、图文一致性和文档产物。

只有用户要求去除 AI 痕迹，或文本明显包含宣传词、机械排比、空泛总结等模式时，再读取 [references/ai-writing-patterns.md](references/ai-writing-patterns.md)。不要默认把所有技术文本当成 AI 文本。

## 不可改变的内容

改写前识别并保护：

- 代码标识、字段名、命令、路径和枚举字面；
- Schema、接口输入输出和状态语义；
- 数字、时间、阈值、范围和前置条件；
- 已验证事实、合理假设与未知项的区别；
- 失败传播、不可变性和权限边界；
- 用户已有的语气、判断和明确取舍。

如果原文与代码或权威文档冲突，先指出冲突。不要靠润色替作者选择事实。

## 处理顺序

### 1. 检查全文结构

先回答：

- 开头是否直接说明目标和范围？
- 标题是否准确提示本节的信息，便于读者定位？
- 内容是否按读者实际经历的顺序展开？
- 重要结论是否出现在支撑信息之前？
- 同一事实是否在多处重复并可能发生分歧？

不要先逐句润色。结构没有修好时，句子变顺只会掩盖问题。

### 2. 还原完整过程

识别文档中的独立工作流。每条工作流选择一个真实入口，并串到可检查的结果：

```text
触发 → 固定输入 → 准备依赖 → 执行 → 收集数据
→ 生成结果 → 检查并保存 → 计算结论 → 返回或发布
```

根据实际系统删减步骤，但不能跳过跨平台提交、等待、回收、校验或失败处理。共享步骤引用唯一主章节，不复制成多套描述。检查每个数据对象是否有生产者、消费者和明确用途。

### 3. 审计词汇

把可疑词分为四类：

| 类别 | 处理 |
| --- | --- |
| 目标读者熟悉的常用词 | 直接使用 |
| 无法替换的专业词 | 保留，首次出现时解释 |
| 只有项目成员理解的内部说法 | 改成具体动作，必要时保留原标识 |
| 删除后含义不变的包装词 | 删除 |

对每个可疑词做四项检查：

1. 新读者能否从字面理解？
2. 能否改成明确的主语、动作和对象？
3. 换成普通词后是否真的损失技术含义？
4. 全文是否始终用它表示同一件事？

不要维护脱离上下文的禁词表。稳定接口名可以保留，无法指向接口、数据或动作的抽象表达通常需要改写。

### 4. 让抽象概念落地

每个重要模块、对象或步骤说明影响正确性的必要信息：

- 谁触发或生产；
- 读取什么；
- 执行什么；
- 产出什么；
- 失败时发生什么；
- 谁继续使用结果。

如果一段只有“负责、支持、提供、承载、打通”，补充可观察的动作和结果。

### 5. 补充最小实例

文字无法回答“具体怎样发生”时，加入最小代码、配置或数据示例。优先展示：

- 跨模块输入和输出；
- 决定正确性的筛选或校验顺序；
- 失败如何传播；
- 业务方法怎样围绕测量窗口组织；
- 配置如何改变运行行为。

标明示例属于当前实现、简化片段还是设计提案。不要复制整份文件，也不要用伪代码假装接口已经确认。

### 6. 改写句子

- 结论先行，再给条件和原因。
- 使用明确主语和主动动词。
- 同一动作始终使用同一个词。
- 一句只承载一个主要判断；条件与结果可以留在同一句。
- 删除不提供事实的强调、铺垫和总结。
- 长短句按内容自然变化，不按字数机械拆句。
- 技术文本不得故意制造松散指代、跳步、拟人或“不完美感”。

自然来自具体和克制，不来自随意。

## 输出方式

- 用户要求修改文件时，直接修改文件，并简要说明改动和验证。
- 用户要求审计时，先列影响理解或决策的问题，再给改写建议。
- 用户只要求改写文本时，直接提供改写结果；变更说明只有在有助于评审时才附加。
- 不默认生成评分、术语表、审计报告或额外交付物。
- 不自动同步、发布或修改派生文档，除非用户明确要求。

## 完成检查

交付前确认：

- 新读者能从真实入口跟到最终结果；
- 重要数据有生产者、用途和失败表现；
- 正文、图表和代码示例表达同一契约；
- 单位、版本、时间、运行身份和唯一键没有跨章节冲突；
- 项目内部说法已改成具体动作或得到解释；
- 同一概念没有换词，同一词没有多种含义；
- 代码标识、数字、条件和边界保持不变；
- 示例足以解释机制，但没有淹没正文；
- 内容重复时保留必要的导航、理由、风险和验收说明，其余引用唯一主章节；
- 改写结果符合原作者语气，而不是统一成某种“AI 反面”风格。
