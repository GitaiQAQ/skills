# 契约一致性与文档产物检查

处理技术方案、接口契约、架构评审或包含图表和代码示例的文档时读取。本检查只验证陈述是否有来源、内部是否一致、产物是否完整；不能仅凭文档决定哪一种技术方案正确。

## 先读取事实来源

涉及实现行为时，先读取可用的权威来源：

1. 当前代码和运行配置；
2. Schema、类型、命令定义和测试；
3. 当前有效的架构或产品文档；
4. 历史说明、注释和归档材料。

不要根据文件名、注释、旧文档或函数名推断真实行为。无法取得来源时，只检查文档内部一致性，并明确说明没有验证实现。

路径含 `archive`、`.agents/archive`、`docs/archive`，或正文明确标为历史的材料，只能用于形成待核对的问题。它不能证明当前行为；必须由前 3 类当前来源再次确认。报告时标明来源等级，不要把历史记录与当前契约并列为同等证据。

## 标明陈述状态

文档中的关键陈述应能归入以下一类：

| 状态 | 写法 |
| --- | --- |
| 已实现行为 | 说明证据来自代码、配置或运行结果 |
| 最终设计 | 明确这是要求实现的稳定契约 |
| 设计示例 | 标明字段或代码经过简化，不代表现有接口 |
| 外部前提 | 说明依赖哪个平台、权限或环境 |
| 合理假设 | 写出假设依据和影响 |
| 待确认项 | 保留未知，不补默认值 |
| 当前进度 | 与最终设计分开，不混入稳定机制 |

不要把设计示例写成当前实现，不要把当前缺失写成最终设计不需要，也不要用将来时掩盖尚未决定的行为。

## 建立契约矩阵

对每个影响正确性的数据对象、命令或组件，检查：

| 维度 | 需要回答的问题 |
| --- | --- |
| 生产者 | 谁创建或返回它 |
| 触发时间 | 在哪个事件或阶段产生 |
| 输入 | 读取哪些事实和配置 |
| 身份 | 用哪些字段证明属于本次运行 |
| 字段 | 哪些字段必填，缺失时怎样处理 |
| 单位 | 数值使用什么单位、基数和精度 |
| 默认值 | 缺失时失败还是使用默认值 |
| 保存位置 | 文件、对象键、数据库或平台记录在哪里 |
| 可变性 | 创建后能否修改，谁有权限修改 |
| 消费者 | 谁读取，读取后执行什么 |
| 失败 | 返回什么状态、原因码或错误 |

不是每个对象都需要在正文逐项列表。只要影响正确性的维度有明确答案即可。不要使用“至少三项”之类数量门槛代替语义判断。

## 跨章节对照

同一契约常在架构概览、流程、Schema、代码示例、验收和附录中出现。逐项检查：

- 生产者和消费者是否一致；
- 输入配置是否来自同一位置；
- 字段名、类型、必填性和默认值是否一致；
- 保存位置和不可变规则是否一致；
- 错误状态和失败传播是否一致；
- 版本、时间点、唯一键和重试身份是否一致；
- 正文、图、表格和代码示例是否描述同一行为。

发现冲突时报告冲突位置和影响。没有实现证据时，不替作者决定哪一处正确。

冲突按证据关系分类：

- **文档内部冲突**：同一份待审文档的两处陈述不能同时成立；
- **当前契约冲突**：待审文档与当前代码、配置、Schema、测试或有效文档不一致；
- **无法验证**：现有来源不足以确认陈述，且来源之间没有形成可证明的矛盾。

三类可以同时出现在一次审阅中，但一条问题只能按其直接证据归入最具体的一类。

## 精确检查易混字段

### 单位与比较

- 百分比、比例、毫秒、秒、字节和兆字节不能只靠字段名猜测；
- 说明比较使用原值、变化量还是变化率；
- 说明严格大于、大于等于或区间判断；
- 示例数字必须标明是否为正式阈值；
- 四舍五入只用于展示还是参与判断必须明确。

### 版本

区分 commit、应用版本、构建版本、Schema 版本、算法版本和工具版本。不要统称“版本”后让读者从上下文猜测。

### 时间

区分创建时间、开始时间、完成时间、截止时间和查询时间。说明使用哪个时区和时间点决定状态。

### 身份与重试

区分运行编号、attempt、repeat 和 retry。说明哪个编号由外部平台生成，哪个编号只在 Runner 内使用，以及重跑是否创建新事实。

### 唯一键与覆盖

说明对象键由哪些字段组成。同键重写、内容冲突、并发写入和幂等重试必须有明确结果。

## 每条工作流独立闭环

不要假设整篇文档只有一条线性流程。分别检查：

- 正常检查；
- 历史结果复查；
- 超时和重试；
- 发布和通知；
- 人工查询和排障；
- 适用时的回滚或恢复。

每条工作流都需要明确入口、输入、结果和失败表现。共享步骤可以引用唯一主章节，不要复制后分别修改。

## 指定事实所有者

重复不是自动错误。关键契约可以在概览、流程和验收中再次出现，但必须指定唯一主章节：

- 主章节完整定义事实；
- 其他章节提供简短摘要并引用主章节；
- 摘要不能引入新字段、新状态或不同说法；
- 图表和代码示例是展示，不成为第二事实来源。

删除重复内容前，确认它是否承担导航、理由、风险提示或验收作用。只删除不增加这些价值的重复。

## 检查图、表和代码

### 架构图和流程图

- 模块名称与正文一致；
- 箭头方向与真实调用或数据流一致；
- 图中没有正文已删除的旧组件；
- 数组、多个实例和可选步骤没有被错误画成单例或必经步骤；
- 直接访问和代理访问的边界一致；
- 图例、颜色和虚实线有必要且含义一致；
- 标题和图注不重复解释图中已经清楚表达的内容。

### 表格

- 同一列使用同一粒度；
- 单元格中的状态和单位明确；
- 长段落不应为了排版硬塞进表格；
- 表格结论与正文一致。

### 代码与配置示例

- 字段名和类型与设计契约一致；
- 省略字段不会改变示例结论；
- 失败分支没有为了简短被删除；
- 示例明确标为当前实现、简化片段或设计提案；
- 示例中的默认值、单位和数组基数与正文一致。

## 检查文档产物

修改文件前读取最新内容，保留用户已有修改。结构调整后检查：

- frontmatter 是否可解析；
- 标题层级和目录是否连续；
- 章节引用、锚点和链接是否有效；
- 图片、附件和相对路径是否存在；
- Markdown 代码围栏是否配对；
- Mermaid 或目标渲染器语法是否受支持；
- 折叠、表格和本地图片是否在目标平台实际可用；
- 删除或移动章节后是否丢失唯一语义；
- 正文、附录和索引是否仍指向当前所有者。

静态语法通过不代表远端文档已经同步或目标平台已经正确渲染。只有实际执行并取得证据后才能报告这些状态。

## 给决策者最小充分上下文

需要读者选择方案或接受风险时，按顺序写：

1. 目标；
2. 当前已确认事实；
3. 各选项对范围、正确性和维护成本的影响；
4. 推荐结论及理由；
5. 读者只需确认的事项。

不要先抛出内部术语、文件路径和待决清单，再让读者自己补齐背景。

## 完成检查

- 关键陈述是否有来源和状态；
- 每个关键契约是否有唯一主章节；
- 跨章节、图、表和示例是否一致；
- 单位、版本、时间、身份和唯一键是否明确；
- 每条独立工作流是否闭环；
- 重复内容是否承担导航、理由、风险或验收作用；
- 文档结构和目标平台渲染是否实际验证；
- 未验证事项是否明确标为未验证。
