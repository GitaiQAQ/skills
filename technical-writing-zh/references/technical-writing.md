# 技术文档审计参考

只在处理技术方案、设计说明、README、操作文档或状态材料时读取。

## 读者任务

技术文档首先服务一个具体任务。常见读者及其关注点：

| 读者 | 主要问题 |
| --- | --- |
| 评审者 | 方案解决什么问题，边界和风险是什么 |
| 实现者 | 输入、输出、顺序、接口和失败方式是什么 |
| 使用者 | 从哪里开始，执行什么，怎样判断成功 |
| On-call | 哪一步失败，去哪里看原始数据，能否恢复 |
| 维护者 | 哪些事实可变，哪些契约不能改，谁拥有它们 |

同一份文档可以服务多个角色，但每一节应有明确读者。不要在实现细节中突然插入面向管理者的价值宣告。

## 标题与定位

标题应准确提示本节信息，让读者不打开正文也能判断是否相关。问题式标题适合解释过程，但不必整篇统一成“怎样……”：

| 含糊标题 | 更准确的标题 |
| --- | --- |
| 全景架构 | 一次检查包含哪些步骤 |
| 执行链路 | 从调度平台触发到报告保存 |
| 数据闭环 | Test Result 怎样生成 Test Report |
| 能力边界 | Runner 做什么，不做什么 |
| 稳定性保障 | 写入失败时怎样处理 |

名称本身就是稳定接口或对象时可以直接作为标题，例如 `Assertion Result` Schema。连续章节使用同一句式但无法体现层级时，改用对象、动作或结果命名。

## 词汇

### 常见包装词

这些词不是绝对禁用。只有无法指向具体对象或动作时才改写。

| 表达 | 先追问 |
| --- | --- |
| 主链 | 哪些步骤按什么顺序执行 |
| 收敛 | 哪些入口、状态或实现被合并 |
| 投影 | 从什么事实派生，供谁读取 |
| 签发 | 谁生成什么结果，是否保存 |
| 封存 | 保存在哪里，之后是否允许修改 |
| 下钻 | 打开哪类原始数据或附件 |
| 装配 | 根据什么配置选择哪个实现 |
| 能力 | 具体可以执行什么动作 |
| 打通 | 哪两个系统通过什么接口通信 |
| 承载 | 具体保存、计算还是展示什么 |

### 保留技术名

满足以下任一条件时保留原名：

- 是代码、Schema 或外部平台的正式名称；
- 替换后无法与实现位置对应；
- 普通词会混淆两个不同概念；
- 读者需要用该名称搜索日志、代码或文档。

首次出现时用一句话解释用途，不需要为每个术语建立词典。

## 过程完整性

先识别正常执行、历史复查、重试、发布、排障等独立工作流，再按实际情况检查各自的断点：

### 触发

- 谁触发？
- 触发条件是什么？
- 使用哪个版本的程序和配置？
- 本次运行如何获得唯一编号？

### 输入固定

- 哪些输入在开始时固定？
- 后续是否可能重新读取变化后的配置？
- 基线、当前版本和期限由谁确定？

### 外部任务

- 请求提交给哪个平台？
- 请求只包含哪些必要字段？
- 怎样区分提交失败、任务失败、状态未知和超时？
- 查询失败是否错误地导致重复提交？

### 数据回收

- 平台成功是否只表示任务结束？
- 回收结果时检查哪些身份字段？
- 怎样证明结果属于本次运行？
- 原始附件保存在何处？

### 报告生成

- 报告由哪些输入组装？
- 哪个组件检查 Schema？
- 报告保存后能否修改？
- 同键不同内容怎样处理？

### 计算与展示

- 判断读取什么事实和规则？
- 机器可读结果、人类摘要与趋势数据是否明确区分？
- 发布失败是否会错误地改变判断结果？

## 抽象层级

正文说明稳定机制和边界，附录列实现文件。不要在正文连续罗列目录、类名和函数名，也不要只画组件框而不解释数据怎样流动。

判断细节是否进入正文：

- 影响正确性、失败语义或模块边界：进入正文。
- 只帮助开发者找到代码：进入附录。
- 只是当前实现进度或迁移过程：除非文档目标要求，否则不进入最终设计。
- 尚未确认的未来扩展：标为待确认，不写成既定机制。

## 重复与引用

重复不是自动错误。重要约束在概览、流程和验收中再次出现，可以帮助不同读者定位。先确定唯一主章节，再处理重复：

- 主章节完整定义事实；
- 其他位置摘要并引用主章节；
- 摘要不引入新字段、新状态或不同语义；
- 保留必要的理由、风险提示和验收要求；
- 删除没有导航、解释或验收价值的重复。

## 代码与示例

一个好的片段通常不超过理解机制所需的范围，并能回答一个明确问题。

适合加入：

- Schema 的关键字段；
- 过滤、匹配和校验顺序；
- 错误映射和失败传播；
- 调用边界；
- 配置到行为的映射。

不适合加入：

- 与主题无关的 import；
- 完整业务文件；
- 纯类型样板；
- 没有调用方的未来接口；
- 为让示例变短而改变真实逻辑的伪实现。

代码片段前说明它回答什么问题，片段后只解释读者无法直接看出的约束。

## 句子和段落

- 段落第一句给结论或动作。
- 同一段只处理一个问题。
- 条件很多时先给结果，再列条件。
- 三步以上的操作使用有序列表。
- 多个可独立检查的条件使用列表或表格。
- 表格用于比较固定维度，不用于塞入长段落。
- 连续短句会割裂因果关系；连续长句会隐藏边界。按语义拆分。

## 事实保护

改写后逐项核对：

- 主语是否变化；
- “必须”是否被改成“可以”；
- “严格大于”是否被改成“大于等于”；
- 同步是否被改成异步；
- 当前实现是否被写成未来设计，或反之；
- 未知条件是否被补成默认值；
- 失败是否被弱化为日志或警告；
- 示例数字是否被误写成正式阈值。

任何一项变化都属于技术修改，不是文字润色。
