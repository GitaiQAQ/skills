# 规模化运营平台升级：为什么要做这件事

在持续变化的业务需求下，平台升级不仅是一次能力调整，也需要形成更加完整的运营支撑体系。

## 双向建联和社群运营的必要性

双向建联和社群运营是规模化运营中的重要组成部分。它们分别从运营团队和合作方两个视角，承载沟通、触达和反馈等目标。

### 从运营视角看

运营团队有几项明确诉求。

- 运营团队希望主动发现合作方的问题，触发相应的运营动作，并及时得到反馈。也就是说，社群可以承载这种双向沟通。
- 对需要触达的合作方，可以通过社群同步活动、培训、教育和治理规则。社群在这里承担统一触达的作用。
- 面向数量较多的中小合作方，运营团队无法提供一对一服务，需要通过社群进行批量运营，提高人效。这样可以支持更大范围的运营动作。

从整体上看，运营侧需要的是能够发现问题、触发动作、及时反馈，并支持批量运营的双向运营通道。

### 从合作方视角看

合作方同样存在多方面需求。

- 合作方希望通过官方渠道与运营团队沟通，并在统一阵地中建立对平台的信任。
- 合作方希望实时反馈运营过程中遇到的问题。
- 合作方需要双向渠道接收平台信息和运营动作。
- 合作方之间可以分享经验，自行解决部分问题。

换句话说，合作方既需要官方、统一的沟通阵地，也需要反馈问题、接收信息和运营动作的双向渠道；同时，合作方之间还可以通过经验分享自行解决部分问题。

### 需求汇总

| 视角 | 主要诉求 |
| --- | --- |
| 运营团队 | 主动发现合作方的问题，触发相应的运营动作，并及时得到反馈 |
| 运营团队 | 通过社群同步活动、培训、教育和治理规则 |
| 运营团队 | 面向数量较多的中小合作方进行批量运营，提高人效 |
| 合作方 | 通过官方渠道与运营团队沟通，在统一阵地中建立对平台的信任 |
| 合作方 | 实时反馈运营过程中遇到的问题 |
| 合作方 | 通过双向渠道接收平台信息和运营动作 |
| 合作方 | 分享经验，自行解决部分问题 |

## 我们要建设什么

规模化运营平台用于连接运营团队、合作方和内容提供者，支持官方建联和批量触达。

从平台承载的目标来看，平台需要完成连接、官方建联和批量触达，并把相关沟通能力统一起来。

相关沟通场景统一接入协作平台，沉淀使用数据，为运营、合作方成长和其他业务提供分析依据。

因此，相关沟通场景统一接入协作平台，使用数据也需要沉淀下来。沉淀的数据将为运营、合作方成长和其他业务提供分析依据。

### 建设内容概括

| 建设方向 | 说明 |
| --- | --- |
| 连接对象 | 运营团队、合作方和内容提供者 |
| 建联方式 | 官方建联和批量触达 |
| 场景承载 | 相关沟通场景统一接入协作平台 |
| 数据沉淀 | 沉淀使用数据 |
| 分析依据 | 为运营、合作方成长和其他业务提供分析依据 |

## 现有建设方式带来的问题

要理解平台升级的必要性，需要先回顾现有建设方式。当前的建联场景主要分为两类。

### 第一类：运营后台建设

在运营后台建设群管理、消息推送等功能，直接提供给运营团队使用，并根据业务需求定制开发。

### 第二类：其他业务建设

由其他业务建设自己的建联场景，规模化运营平台只提供封装后的建联 API。

这两类方式分别对应运营后台直接使用，以及其他业务自行建设场景、平台提供封装后的建联 API。现有模式能够支持不同接入方式，但也带来了以下四个问题。

## 四个核心问题

### 问题一：通用能力没有形成复用能力

入驻、群管理、消息触达和常用应用具有较强通用性，但没有经过抽象形成可复用能力。

也就是说，这些具有较强通用性的能力还没有通过抽象完成复用能力的沉淀。

### 问题二：定制逻辑较多，职责边界不清晰

每接入一个业务场景都需要开发大量定制逻辑，没有明确区分平台职责和接入方职责。

这使得业务场景接入需要大量定制开发，同时平台职责与接入方职责也没有被明确区分。

### 问题三：数据沉淀不足，长期价值难以形成

平台主要提供 API，没有沉淀足够的业务数据，难以形成长期价值。

换句话说，当前平台更多是提供 API，业务数据沉淀不足，因此长期价值难以形成。

### 问题四：能力分散，缺少统一平台

各场景和服务能力相互分散，缺少统一平台来聚合业务域并形成整体认识。

各类场景与服务能力没有被统一聚合，也就缺少一个统一平台来聚合业务域并形成整体认识。

### 问题汇总

| 问题 | 具体表现 |
| --- | --- |
| 通用能力未复用 | 入驻、群管理、消息触达和常用应用具有较强通用性，但没有经过抽象形成可复用能力 |
| 定制逻辑较多 | 每接入一个业务场景都需要开发大量定制逻辑，没有明确区分平台职责和接入方职责 |
| 数据沉淀不足 | 平台主要提供 API，没有沉淀足够的业务数据，难以形成长期价值 |
| 能力相互分散 | 各场景和服务能力相互分散，缺少统一平台来聚合业务域并形成整体认识 |

以上问题共同说明，现有建设方式在能力复用、职责划分、业务数据沉淀和统一聚合方面仍需要升级。

## 平台升级思路

为适应持续变化的业务需求，需要对现有环节进行梳理，并形成更加标准化、可组合的能力组织方式。

具体来说，需要梳理入驻、社群、消息和应用等环节，标准化基础模型，抽象建联流程，并把业务能力封装成可组合的场景组件。

这些动作可以进一步打通平台能力：

1. 梳理入驻、社群、消息和应用等环节。
2. 标准化基础模型。
3. 抽象建联流程。
4. 把业务能力封装成可组合的场景组件。

平台由此能够快速支持不同场景，同时保留扩展能力。也就是说，平台既要支持不同场景的快速接入，也要保留后续扩展能力。

## 服务单元的定位

服务单元是实现最小业务目标的标准基础模型，应具备较强通用性。

从基础模型的角度看，服务单元承载的是最小业务目标；从复用和扩展的角度看，服务单元应具备较强通用性。

## 核心价值总结

平台升级的核心价值可以归纳为以下几个方面：

| 核心价值 | 对应内容 |
| --- | --- |
| 支持双向沟通 | 通过社群承载运营团队与合作方之间的双向沟通 |
| 支持批量运营 | 面向数量较多的中小合作方进行批量运营，提高人效 |
| 统一官方建联 | 连接运营团队、合作方和内容提供者，支持官方建联和批量触达 |
| 沉淀分析依据 | 统一接入相关沟通场景并沉淀使用数据，为运营、合作方成长和其他业务提供分析依据 |
| 提升能力复用 | 标准化基础模型、抽象建联流程，并封装可组合的场景组件 |
| 保留扩展能力 | 让平台快速支持不同场景，同时保留扩展能力 |

总体而言，规模化运营平台需要通过平台升级，承载双向建联和批量运营，打通相关沟通场景，沉淀使用数据，并以标准基础模型和可组合的场景组件支撑持续变化的业务需求。
